## 1. Vision and principles

- Anyone in the organization can use small HTML apps ("views") built in ~10 minutes through an AI chat, or uploaded from disk.
- Goal: replace clumsy shared Excel/Word files with tiny purpose-built tools (e.g. a team presence calendar where everyone marks office days and days off).
- **Apps are disposable.** They save time daily but are not critical. A broken app is fixed by re-prompting, not treated as an incident. Nobody should feel bad deleting one.
- **Data is durable.** Data is the only thing that cannot be regenerated by a prompt, so it is protected (history, backups). When an app is rewritten, its data is converted to the new format (AI-driven migration).
- **Lightweight over complete.** No visual builder, no component library, no optimization. Fast and cheap beats polished.
- **Anything that runs natively in a browser must work.** No special format required for apps. A plain HTML file generated elsewhere and uploaded from disk must work.
- **Accepted risk:** apps may read each other's data, so changing one app can break another. This is a conscious trade-off. Mitigation is visibility (dependency log), not prevention.
- **Not accepted:** data leaving the company. Apps may only work within the company database. No internet access from apps.
- **No extra per-user licenses.** End users never need an account with an AI vendor. The only LLM cost is a single API key billed per token, used only when building.

## 2. Users and roles

| Role | Who | Can |
| --- | --- | --- |
| User | Any authenticated employee | Open apps, read/write data through apps |
| Builder | Members of an AD group (e.g. `shitcloud-builders`) | Use the AI chat, deploy/upload apps, run migrations, restore data from history |
| Admin | Platform owner | Archive/delete apps and spaces, manage API key, limits |

Authentication is through the organization's identity provider (OIDC). Test: any OIDC provider (Google, or Keycloak in a container). Target on-prem: Active Directory via ADFS (OIDC) or Entra ID if hybrid — to be confirmed with admins. Builder role comes from the `groups` claim. Every write records the user id.

## 3. Tech stack (decided)

- **Backend:** Spring Boot (Java 21), single deployable JAR. Spring Security (OIDC client), Spring Data MongoDB using `MongoTemplate` (repositories are too rigid for dynamic collections), Spring AI with Anthropic Claude.
- **Database:** **MongoDB** (Community Edition). Chosen deliberately so the owner can learn Mongo (previous NoSQL experience: Elasticsearch only). Run as a **single-node replica set** (`mongod --replSet rs0` + one-time `rs.initiate()`) to enable multi-document transactions and change streams at the cost of one instance.
- **Frontend (platform UI):** **React SPA built with Vite**, served as static files by Spring Boot. Build integrated into Maven via `frontend-maven-plugin` so the output is still one JAR. Thymeleaf is NOT used.
- **AI chat UI:** a **separate, reusable React package** (also publishable as a web component) so it can be embedded in other apps. Evaluate existing React LLM chat libraries (e.g. assistant-ui, Vercel AI SDK UI) before building from scratch; check which streaming protocol they expect, because the Spring endpoint must emit it.
- **AI chat backend:** a **separate Spring module** with a generic API (conversation, streaming via SSE, pluggable tool registration). ShitCloud-specific tools are one plug-in set, so the chat is reusable outside ShitCloud.
- **LLM:** Claude via API, one key in an environment variable. No end-user Claude accounts.
- **Test hosting:** Railway (MongoDB from Railway's database template + Spring Boot service from GitHub).
- **Target hosting:** company on-prem with AD SSO.
- **RAG:** deferred. When needed, use MongoDB Community Search/Vector Search (requires the separate `mongot` process, MongoDB 8.2+). Not part of MVP.

## 4. Architecture

```
Browser
 ├─ Platform SPA (React) on platform origin, e.g. shitcloud.company.tld
 │    ├─ App list, builder panel, AI chat (reusable package)
 │    └─ Host page: header + <iframe> pointing at the app origin
 └─ App (any HTML/JS) on its OWN origin, e.g. {slug}.apps.company.tld
      └─ Injected SDK (window.shitcloud) → postMessage → host page → REST API

Spring Boot (one JAR)
 ├─ Auth (OIDC, groups → roles)
 ├─ App registry + deploy/upload + versions
 ├─ App serving (per-app origin, SDK injection, CSP)
 ├─ Data API (Mongo-style filters, whitelist, history, dependency log)
 ├─ Chat module (Spring AI, SSE, tools)
 └─ Migration runner (sandboxed JS, e.g. GraalJS)

MongoDB (single-node replica set)
External: Claude API (only outbound traffic), company IdP
```

### 4.1 App isolation (non-negotiable)

- Each app is served from **its own origin** (subdomain per app: `{slug}.apps.company.tld`), on a different domain than the platform. This lets apps use `localStorage`, IndexedDB, cookies etc. normally while staying isolated from the platform and from each other.
  - Requires wildcard DNS + wildcard TLS certificate. **Verify** whether Railway's plan supports wildcard custom domains; if not, use a fallback for the test environment (e.g. one shared apps domain separate from the platform domain, accepting that apps share an origin with each other on test only).
- The iframe uses: `sandbox="allow-scripts allow-same-origin allow-forms allow-modals allow-popups allow-downloads"`. No `allow-top-navigation`. (Without `allow-modals` even `alert()` fails; without `allow-downloads` CSV export fails.)
- Apps never call the REST API directly and never see the platform session. All data access goes through `postMessage` to the host page, which validates `event.origin`/`event.source`, maps the request to the app slug, and calls the API with the user's session.
- **CSP on app responses:** `connect-src 'none'` (hard rule: no network calls out of the app). Scripts, styles, fonts and images only from the app's own origin and the platform's **locally hosted library mirror** (no external CDNs; on-prem may have no internet anyway). Inline scripts/styles allowed (single-file apps rely on them).
- Security is enforced by browser mechanisms (origin, sandbox, CSP), **never by the AI agent alone**. The agent adapts apps to the rules; it is not a security control (uploaded HTML may contain prompt injection).
- Note for stakeholders: "the uploader is responsible" is fine for accidental breakage but does not cover data leaks. The company is the GDPR (RODO) data controller; e.g. a presence calendar with a "sick leave" category contains health data. Keep `connect-src 'none'`.

### 4.2 Platform UI screens (React SPA)

1. **App list:** name, owner, last used, open button, archived filter.
2. **Host page:** app name bar + iframe + postMessage bridge. Mandatory, because the bridge lives here.
3. **AI chat for building:** conversation on the left, live preview (same sandbox/origin model as production) on the right, "Deploy" button outside the chat.
4. **Upload from disk:** single HTML file or ZIP (for apps referencing local assets like `style.css`, `logo.png`), then the import flow (section 7).
5. **Builder panel:** document history with restore, migration summaries, dependency list per space.

## 5. Data model (MongoDB)

Database `shitcloud`. Platform collections prefixed with `_`. App data lives in one shared collection partitioned by `space`.

| Collection | Contents | Notes |
| --- | --- | --- |
| `_apps` | slug, name, owner, current HTML (or asset pointer), `lastUsedAt`, `archived`, token usage counter | One doc per app |
| `_app_versions` | appId, version, HTML/assets, author, date | Written on every deploy; TTL ~90 days |
| `docs` | `space`, `collection`, `_id`, `data`, `version`, `updatedBy`, `updatedAt` | All app data; compound index `{space, collection, _id}` plus indexes as needed |
| `_history` | `space`, `collection`, `docId`, `version`, `op`, `data` (previous state), `changedBy`, `changedAt` | Previous document versions; TTL index on `changedAt` (~90 days) |
| `_deps` | `appId`, `space`, `mode` (read/write), `lastSeenAt` | Upserted on every data call |
| `_migrations` | appId, old space, new space, transform function source, result counts, status | Audit of AI migrations |

Rules:
- **Space** = data namespace owned by an app (default = app slug). Inside a space, apps create their own collections freely, no schemas.
- **Write only to own space.** Read access to other apps' spaces is allowed and logged in `_deps`.
- **History:** before every update/delete, the Data API writes the previous version to `_history` **in the same transaction** as the write (single-node replica set enables this). `version` increments on each write and doubles as optimistic locking.
- **TTL indexes** clean `_history` and `_app_versions`; no cron jobs.
- **App lifecycle:** app unused for 30 days → `archived: true`. Its data is never deleted automatically.
- Indexes and TTLs are created at application startup (`MongoTemplate.indexOps`), not by manual scripts.
- Backups: always back up all data. Test: daily `mongodump` to a bucket, or Railway volume backups if available on the plan (verify). On-prem: `mongodump` cron into the existing backup system; test a restore once before launch.

## 6. API and SDK

### 6.1 REST endpoints (all authenticated)

| Method and path | Purpose |
| --- | --- |
| `GET /api/apps` | List apps |
| `POST /api/apps`, `PUT /api/apps/{slug}` | Deploy new version (builders only); accepts HTML or ZIP |
| `GET /api/apps/{slug}/versions` | Version list |
| `POST /api/data/{space}/{collection}/query` | Find with filter, sort, limit |
| `PUT /api/data/{space}/{collection}/{id}` | Upsert document, writes history |
| `DELETE /api/data/{space}/{collection}/{id}` | Delete, writes history |
| `GET /api/history/{space}/...` and `POST .../restore` | History browsing and restore (builders) |
| `GET /api/deps/{space}` | Which apps read/write this space |
| `GET /api/me` | Login, display name, groups |
| `POST /api/chat` | Chat (SSE stream), served by the chat module |

App serving on the app origin: `GET https://{slug}.apps.../` returns the app HTML with the SDK injected and the CSP header set.

The server always sets `space`/`collection` in queries from the authenticated app context; never trust them from the app payload for writes.

### 6.2 Filter language

Mongo-style filters passed through a **whitelist of operators**: `$eq, $ne, $gt, $gte, $lt, $lte, $in, $nin, $exists, $and, $or`. Reject `$where`, `$function`, `$expr` with JS, and anything not on the list. Translate to Spring `Criteria`. Rationale: LLMs generate Mongo filter syntax correctly on the first try.

### 6.3 JS SDK (injected, ~30–50 lines)

- Injected as the **first `<script>`** in every served app. Must be invisible: an uploaded HTML that knows nothing about the platform must keep working unchanged.
- Single namespaced global `window.shitcloud` — never a bare `db` global (collision risk).

```js
const me = await shitcloud.me();
const days = await shitcloud.db.find('days', { userId: me.id, date: { $gte: '2026-10-01' } });
await shitcloud.db.set('days', 'filip_2026-10-20', { type: 'off' });
await shitcloud.db.remove('days', 'filip_2026-10-20');
const other = shitcloud.db.space('presence-calendar'); // read-only access to another app's space
```

- Transport: `postMessage` to the host page with request ids and promise resolution.
- No realtime in MVP; apps poll every few seconds if they need fresh data.

## 7. AI features

### 7.1 Build chat

- Spring AI + Claude API, tool calling, SSE streaming.
- The model returns the **whole HTML file** each time (apps are a few hundred lines; diffs are unnecessary complexity at this scale).
- System prompt contains: full SDK documentation with examples (the single most important artifact of the project — iterate on it), rules (single file, no `fetch` to external URLs, libraries only from the local mirror, UI labels in Polish), a default stack recommendation for consistency (e.g. vanilla JS or Alpine + Tailwind from the local mirror), and a list of existing spaces with short descriptions.
- Tools:

| Tool | Purpose |
| --- | --- |
| `list_spaces` | Spaces, their collections, document counts |
| `sample_docs(space, collection, n)` | A few real documents so the model learns the data shape (no schemas exist) |
| `get_app(slug)` | Current HTML of an app to rework |
| `save_draft(html)` | Refresh the preview |
| `get_deps(space)` | Which apps read a space, to warn before changing data shape |
| `propose_migration(fn)` | JS transform `oldDoc → newDoc` |

- Before changing a data shape, the model warns, e.g. "3 apps read this space; changing field `status` will likely break 2 of them". It informs; it does not block.
- Cost control: daily token limit per builder; usage counter.
- Prompts may contain samples of company data sent to the LLM vendor. This requires company approval of the API vendor before the pilot. Prefer schemas/samples over bulk data in prompts.

### 7.2 Data migration on app rewrite

1. Model writes a transform function and calls `propose_migration`.
2. Platform runs it in a JS sandbox (e.g. GraalJS, no I/O) over all documents of the old space into a new space.
3. Chat shows: documents in, out, failed, plus 3 before/after examples.
4. Builder clicks OK.
5. Old space stays **read-only for 30 days**, then is removed.

### 7.3 Import of HTML from disk

Users can upload any HTML (or ZIP). Before deploy, an agent adapts it to platform rules while preserving look and functionality:
- External CDN libraries → replaced with the local mirror copies.
- External fonts/images → embedded or replaced with system fonts.
- `fetch` to external APIs → removed or rewired to the SDK if the data exists in the company DB; otherwise reported as a feature that will not survive.
- `localStorage` persistence and hard-coded data in JS → moved to the SDK (this is the main value: a personal file becomes a shared team app).
- The agent must output a **change list** (what changed/removed and why).
- UI shows **before/after preview side by side**; a human accepts.
- Size limit with a clear message for very large files (e.g. exported dashboards of several MB that exceed model context). Later option: deploy as a static document without DB access (works under strict CSP if it needs no network).

## 10. Risks and conscious trade-offs

| Risk | Decision | Mitigation |
| --- | --- | --- |
| Changing one app breaks another | Accepted | Warnings from `_deps` in chat |
| AI migration silently loses records | Not accepted | Count summary, human approval, old space read-only 30 days |
| Someone overwrites others' data | Accepted | `updatedBy` + restore from `_history` |
| App code exfiltrates data | Not accepted | Separate origins, sandbox, CSP `connect-src 'none'`, local library mirror |
| Prompts with data reach the LLM vendor | Needs company approval | Samples/schemas only; approval before pilot |
| Throwaway apps become de facto production | Accepted | Data is durable and portable; apps regenerate from prompts |
| Bus factor = 1 | Resolve before on-prem | Formal owner in IT |
